# Editor

The writing surface is vanilla CodeMirror 6 (no React wrapper), parsed by Lezer's markdown grammar. This doc covers the rules for touching `Editor.tsx`, how highlighting works and where it doesn't, and how edits get to disk without losing anything. Each extension in `src/lib/editor/extensions/` has a header comment explaining what it does and why; read those for detail.

## One Lezer, one CodeMirror

Only one copy of `@lezer/common` and of each `@codemirror/*` package may be installed. Lezer's `Tag` and tree objects from different versions aren't compatible, so a duplicate breaks highlighting at runtime without an error, and a duplicate `@codemirror/view` breaks typecheck. `package.json` pins `@lezer/common` with `overrides`, but `bun update` can still leave older copies nested under other packages. AGENTS.md has the check and the fix.

## Editor.tsx

`Editor.tsx` owns the `EditorView` by hand, and the store mirrors it rather than driving it:

- **The view is created once** (an effect with empty dependencies). Recreating it would lose undo history, selection and scroll.
- **Typing flows editor → store.** The update listener writes `editorContent` to the store, which marks the file dirty and schedules auto-save.
- **Everything else flows store → editor through `useEditorStore.subscribe`,** not a React subscription, so typing never re-renders the component. It's wrapped in `React.memo` with a comparator that always returns `true` for the same reason.
- **Store-to-editor writes set `isProgrammaticUpdate`** so the update listener doesn't mistake them for typing. Without it, loading a file would mark it dirty and save it straight back.
- **A store write that differs from the document replaces the whole document.** That loses the scroll position (and typewriter mode re-centres on any `docChanged`), so it should only happen when a file is opened or changed on disk. See the round trip below.
- **Modes** (focus, typewriter, the Alt key for URL and image hover) are toggled with state effects, not by recreating extensions.

## Highlighting

Highlighting runs through custom tags rather than `@lezer/highlight`'s built-in `tags.*`, so headings, emphasis and their syntax marks can be styled separately:

- `syntax/markdownTags.ts` defines the tags;
- `syntax/styleExtension.ts` maps Lezer nodes to them with `styleTags`;
- `syntax/highlightStyle.ts` maps tags to styles.

**Contextual mark rules don't fire.** Since `@lezer/highlight` 1.2.3, `@lezer/markdown`'s built-in rule (every mark → `tags.processingInstruction`) is checked before ours, so a rule like `'ATXHeading1/HeaderMark'` in `styleExtension.ts` is silently ignored. `extensions/syntax-mark-decorations.ts` works around this by walking the tree and decorating heading, emphasis and strong marks directly, and `theme.ts` gives those classes `inherit !important` to beat the inner highlight spans. Style any new contextual mark the same way.

`styleTags` also only applies to the exact node, not its children, which is why whole-blockquote styling is a line decoration (`blockquote-style.ts`).

Colours and type come from `editor-styles.md` and the `--editor-color-*` tokens in `App.css` (see `color-system.md`).

## Grammar and spelling

Harper (`harper-core`, pinned to an exact version in `src-tauri/Cargo.toml`) checks the body text in Rust; `extensions/grammar.ts` shows the results through `@codemirror/lint`, and `lib/grammar/` maps them to underlines, popup buttons and ignored issues.

- **Rust, not harper.js.** The WASM build is a 94 MB npm package (about 18 MB of WASM to bundle), needs `wasm-unsafe-eval` in the CSP and had never been tried in WKWebView. Natively, 5,000 words take about 50 ms once warm (about 0.4 s for the first check of a file in a release build).
- **One worker thread** (`commands/grammar.rs`) runs every check, and only the newest of several waiting; the others get `null` and the editor keeps what it shows. Harper builds its spelling automaton once per thread, which took seconds on fresh blocking-pool threads. The checker is rebuilt (a few hundred ms) only when the dialect or the dictionary changes.
- **Offsets:** Harper counts in Unicode chars and CodeMirror in UTF-16 code units, so Rust converts at the boundary. Anything that moves issue ranges must keep `utf16_offsets_after_emoji_and_accent` passing.
- **What's skipped:** frontmatter and the MDX import block never reach the editor; Harper's Markdown parser skips code, URLs and HTML. For MDX, `mask_mdx` blanks `import`/`export` statements at the start of a block, component tags (including multi-line ones) and `{expressions}` with spaces, so the text inside a component is still checked, and issues touching a blanked range are dropped. Then `strip_indentation` removes every line's indentation, keeping a map back to the original offsets: MDX has no indented code blocks, but Harper does, so text indented inside `<TabItem>` was skipped as code. Files over `GRAMMAR_MAX_CHARACTERS` (250,000) aren't checked; a quiet note under the text says so.
- **A panic in Harper** is caught on the worker thread (`catch_unwind`; the release profile unwinds for this): that check returns no issues, the checker is rebuilt, and the same text isn't checked again until it changes.
- **Rules:** Harper's curated set, minus `UseTitleCase` and `LongSentences` (`RULES_OFF`), which underline a whole heading or sentence for house style. Overlapping issues keep one: a misspelling first, then the shorter range, so a broad issue can't hide a typo.
- **The popup** (`extensions/grammar-popup.ts`) opens on hover, on click and with Cmd+. (Ctrl+.) at the cursor, which focuses the first suggestion; Escape closes it. It reuses the lint package's classes, but the package's own hover tooltip is off (`tooltipFilter`). Tooltips mount on `document.body`, because the editor's panel clips them. A suggestion or Ignore whose text changed since the check does nothing and re-checks.
- **Settings** are read with `getState()` on every check, and again when it returns (switched off meanwhile: nothing is shown; dictionary words are filtered in the editor too); `useGrammarRefresh` re-checks when they change. Ignore is per file (it follows a rename) and lasts until the app quits. Add to dictionary writes `grammar.dictionary` in global settings (see `app-data.md`).
- **Dev builds** optimise Harper's crates (`[profile.dev.package.*]` in `Cargo.toml`); unoptimised they're 10 to 20 times slower. `cargo test --lib grammar::tests::timing -- --ignored --nocapture` prints timings for a 5,000-word file.

## Auto-save and data safety

Never losing work is a product principle, and most of these rules were written after a data-loss bug.

- **When it saves:** `scheduleAutoSave` in `editorStore.ts` debounces by the `autoSaveDelay` setting (2 seconds by default). Debouncing alone never fires during continuous typing, so a save is also forced once 10 seconds have passed since the last one (`MAX_AUTO_SAVE_DELAY_MS`). `openFile` sets `lastSaveTimestamp` so that clock starts when a file opens.
- **Who saves:** the store can't call hooks, so Layout registers `useEditorActions().saveFile` as the store's auto-save callback (the Hybrid Action Hooks pattern, see `architecture-guide.md`). Auto-save never shows the success toast (it saves with `showToast` false); a failed save still shows an error.
- **Switching files saves first.** `openFile` runs the save for a dirty file before replacing the store's state, and opening the file that's already open (matched by path) only selects its collection: clearing the store would wipe unsaved edits, and a saved file would stay blank, because its cached content query doesn't load it again. A save that finishes after the switch only updates the store if its file is still open; if it fails, the recovery data is the outgoing file's.
- **Quitting saves first.** Every way of quitting (Cmd+Q, the Dock, logout and shutdown on macOS; closing the window or Exit on Windows and Linux) makes Rust emit `quit-requested` instead of exiting. `answerQuitRequest` in `lib/quit.ts` saves the open file and calls `quit_app`. If the save fails it calls `cancel_quit` and asks whether to quit anyway, since recovery files can't be restored from the app. Rust quits by itself if the frontend doesn't answer within 5 seconds, so a hung webview can't make the app unquittable. Restarting to install an update calls `saveUnsavedEdits` first too. The Rust side, including the macOS hook, is `src-tauri/src/commands/quit.rs`.
- **Edits during a save survive.** After writing, `saveFile` marks the file clean only if the content and frontmatter in the store still match what it wrote. Anything typed while the save was in flight stays dirty and is saved next time.
- **Body-only edits keep the user's YAML.** If the frontmatter wasn't touched (`isFrontmatterDirty`), the save sends the original `rawFrontmatter` text, so formatting, comments and key order are preserved. Only an edited frontmatter is re-serialised, in schema field order.
- **Undone edits leave the file as it was.** Re-serialising changes quoting and spacing, so a toggle switched on and off would still show as a change to publish. The store keeps `frontmatterBaseline`, the values and exact text from the first load after opening, and `frontmatterToWrite` (`lib/frontmatter-save.ts`) sends that text instead of the values whenever they're deep-equal to it. The baseline moves to any later load except the reload of our own save (recognised by `lastWrittenFrontmatter`, the values that save wrote), so a change made outside the app or by git becomes the new starting point. A key the file never had counts as unchanged while it only holds its default (the schema's, or false for a switch, an empty list or empty text), so switching a new toggle on and off again also leaves the file alone.
- **Unsaved edits win over disk.** When the file content query refetches, `useEditorFileContent` only copies it into the store if the file isn't dirty. `useFileChangeHandler` ignores watcher events for a dirty file and for 3 seconds after our own save, because one save can produce several events. Every other watcher event also refreshes the sidebar and entry pickers, so files added, renamed or edited outside the app show up. The collection counts (`useCollectionFileCountsQuery`) are keyed apart from the entry pickers' file lists, because counting walks the whole folder: the watcher refreshes only the counts of the collections holding a file that was created, removed or renamed, once per collection when a burst of events ends (a Sync or checkout sends one event per file), and saves never refresh them.
- **The save round trip must be byte-identical.** After a save, the content query refetches the file. If parsing it back gives even slightly different text than the editor holds, the store write replaces the whole document and the view jumps. Trailing newlines did exactly this: the save added one and the parser dropped one, so the view jumped every few seconds. The round-trip tests in `src-tauri/src/commands/files.rs` (`test_roundtrip_*`, and `mdx_corpus_tests` over the files in `test/mdx-imports/`) cover it; any change to parsing or serialising must keep them passing.
- **MDX imports are hidden, not edited.** `parse_frontmatter` splits an MDX file into frontmatter, the ESM block (its `import` and `export` statements) and the body. Only the body reaches the editor. `src-tauri/src/mdx_esm/` finds where the block ends by parsing it with swc, the way MDX does, and the block is written back as read. A block that ends in the wrong place either hides text the writer can't then edit or shows code in the editor, so check any change against the corpus snapshot in `test/mdx-imports/files/blocks.txt`.
- **If a save fails,** the file stays dirty and recovery files are written (see `app-data.md`). There's no crash recovery.
- **File names follow titles only on request.** New File names the file from the title (`lib/files/new-file.ts`). For an existing entry, "Update to …" under the title field, "Rename File to Match Title" in the palette and "Rename to Match Title" in the sidebar's menu all run `renameCurrentFileToTitle` (`lib/files/rename-to-title-action.ts`); nothing renames by itself. The palette command and the menu item are offered for any file whose title has letters or digits and whose name isn't its slug (or its slug plus a `-1`, `-2`). The hint under the title is narrower, so it doesn't nag on a site whose files were never named after titles: only when the file was named after its title as loaded (`frontmatterBaseline`, or `titleBaseline` after a rename) and the title has been changed since (`titleEditedAwayFromName`). The action takes the target from `renameTargetFor` (same slug rules and collision numbers as New File, same extension, other files in the folder), sets a text `slug` field to the new name, saves unsaved edits (including that slug) and only then renames on disk with `rename_file`. `updateCurrentFileAfterRename` updates the open entry's path, name and id together, because the sidebar picks the open entry by id. A failed save leaves the name alone.
