# Git panel

The frontend of the optional publishing tools: the **Changes** tab in the left sidebar, **Publish** in the title bar, diffs and **History** in the main area, GitHub sign-in, pull requests and **Open from GitHub**. The Rust side (libgit2, the GitHub API, the Keychain, safety rules) is in `git-and-github.md`.

## Switched off by default

Everything here is behind the General preference **Show preview and publishing tools** (`general.showPublishingTools`, default `PUBLISHING_TOOLS_DEFAULT` in `defaults.ts`, `true` in this fork), read with `useShowPublishingTools()`. While it's off:

- no git or GitHub query runs (each query hook checks the preference in `enabled`);
- the sidebar has no tabs and renders the Files panel exactly as before;
- Publish, the GitHub preferences pane, the sign-in sheet, the Open from GitHub dialog and the palette's Publishing commands are absent.

Gate new UI the same way, so turning the preference off leaves the app as it was.

## State

- **`gitStore`** (`src/store/gitStore.ts`) holds what the panel shows: the sidebar tab (`files` | `changes`), the diff or History shown over the editor (one at a time), the selected commit and commit file, the sign-in sheet's state, and whether the new-branch and Open from GitHub dialogs are open. Layout calls `reset()` when the project changes; sign-in and Open from GitHub survive that.
- **Queries** live under one key prefix, `queryKeys.git(projectPath)` (`['project', path, 'git', …]`), so `refreshGit()` (`lib/git/cache.ts`) refreshes status, branches, history, diffs and pull requests together after any command that changes the repository. Index 4 of every git key is a constant, never a path or id, because `useFileChangeHandler` invalidates keys with `'files'` at index 4. Sign-in (`githubAuth`) and the repository list (`githubRepos`) aren't tied to a project.
- Command results go through `unwrap()` (`lib/git/unwrap.ts`): Rust returns plain-language messages, so an error's message is shown to the writer as is, in a toast or in the panel.

## Changing the repository safely

Every mutation that changes the repository (publish, sync, checkout, "Bring in changes", merging a pull request) shares `GIT_CHANGE_MUTATION_KEY` and goes through `lib/git/repo-change.ts`:

- **It saves the open file first** (`saveBeforeGitChange`, using `saveUnsavedEdits` from `lib/quit.ts`). Unsaved edits saved after a checkout or sync would silently undo the incoming changes. If the save fails, nothing runs. A failed save has usually said why (the editor counts those in `saveFailures`), so the git mutation adds no second toast; when it didn't, `saveBeforeGitChange` shows "Couldn't save your edits, so nothing was changed."
- **While it runs, nothing can be edited**: `useGitEditGuard()` makes the editor area and the frontmatter panel `inert`, and the panel disables Sync, Publish, Bring in, Discard, the branch menu and the message box. Tauri's file drops are window-wide and ignore `inert`, so the editor and image pickers check `isGitBusy()` (`lib/git/busy.ts`, the non-React twin of `useGitBusy`), as do the component builder and content linker shortcuts. Focus is remembered as the operation starts (before React applies `inert`, which takes it away) and put back afterwards, if it was in one of those areas and the writer hasn't gone elsewhere.
- **Afterwards it reloads what git rewrote** (`reloadProjectFiles`, after checkout, sync, bring in, resolve, discard and a publish that merged or fast-forwarded), the open file first, then collections, collection file lists and folder listings. `onSuccess` awaits it, so the mutation, and the block on editing, only ends once the editor holds the new text. The watcher can't be relied on here, because it ignores the open file for a few seconds after our own save, which just happened. It does nothing if another project opened meanwhile, and closes the open file only if it's gone (it doesn't exist on the branch) and has no unsaved edits.

## Keeping the status current

Coming into view, the Changes tab fetches too (`fetchIfStale`, when signed in, unless a fetch ran in the last 30 seconds), and a line under the branch summary says when GitHub last answered ("Checked just now", "Checked 3 min ago"; `gitStore.checkedAt`, set by every successful fetch, sync and push).

`loadGitStatus()` (`lib/git/status.ts`) is the status query's function. It reads the local status, so the panel and the title bar's Publish appear at once; it never waits for sign-in or the network. When the writer is signed in and the project hasn't been fetched for about five minutes (`FETCH_INTERVAL_MS`, with 30 s of slack for timers; kept per project), it starts a fetch in the background after the local read, and the fetched status replaces the cached one when it arrives (branches, history, pull requests and the behind-default count are reloaded too). Git commands on one repository run one at a time on the Rust side, so a status read can wait behind a running Publish or Sync; the panel keeps showing the last status meanwhile. A failed fetch only logs a warning. The query reads the sign-in state when it runs, and `useGitStatusRefresh` reloads it once sign-in is confirmed, so the first fetch after opening a project happens as soon as it can.

`useGitStatusRefresh()` (mounted once, in Layout) reloads the status, and any open diff of a changed file, on `file-changed` (the watcher), on window `focus`, and every five minutes while `document.hasFocus()`. It's our own interval rather than TanStack's `refetchInterval`, because TanStack's focus manager follows page visibility, and a Mac app's page stays visible when the app is in the background.

"Bring in changes from main" is offered only when `gitCommitsBehindDefault` says the default branch has commits the current branch doesn't.

## Components

In `src/components/git/`:

- **`ChangesPanel`** wires queries and mutations to **`ChangesView`**, which is presentational so the styleguide can show every state with fixtures. Keep new state in the container and new display in the view.
- **The Publish message** is pre-filled by `publishMessage` (`lib/git/changes.ts`) until the writer edits it, without an effect: the panel keeps a `draft` that's `null` until edited. It names entries by their frontmatter titles only, never file names: "Add Harbour, update About and images", at most three names then "and N more"; an entry without a title (usually a deleted one) is counted, "remove 1 entry", never named by its file; assets aren't named ("and images", or "Update images" when nothing else changed). Titles come from `useEntryLookup`, which reads the same per-collection file lists as the entry pickers.
- **Engine messages are presented** with `presentGitMessage` (`lib/git/messages.ts`): paths of known entries become their titles, and "the remote" becomes "GitHub" when it is.
- **Each outcome is shown once.** A conflict or a blocked sync, publish or "Bring in changes" becomes a notice in the panel (switching to the Changes tab if it's out of sight, as after the palette's Publish), not a toast. The notice belongs to its branch.
- **Conflicts with GitHub's copy have a way out.** When the branch and its upstream both have new commits, `useGitConflictsQuery` asks the engine which files conflict (an in-memory merge; a background fetch reloads it too). A Publish or Sync that stops on a conflict opens **`ResolveConflictsDialog`**. For each file it says what differs in plain words (`conflictSummary` in `lib/git/conflict-summary.ts`: the changed fields by label with both values, and the lines of the text that differ; images say "Image"), with **Keep mine** or **Use GitHub's** ("the other version" when the remote isn't GitHub). **Show full versions** shows both whole files with the changed lines marked (`lineDiff`). The choices start again whenever the list changes (the form is keyed on it). **Combine and publish** runs `gitResolveConflicts` (save-first and the edit guard apply) and publishes straight away.
- **Your version always has your latest edits.** Edits made after the conflict aren't in the conflicting commit, so when the dialog opens, and again before Combine, any uncommitted change is committed first with Publish's own commit step (it commits, tries, and stops on the conflict with the commit kept), and the list is read again. If that changed the list, Combine stops and asks to check the choices again. Every outcome stays in the dialog, as a message at its top: a blocked combine, an error, or GitHub having moved again (the fresh list is shown with "Choose again for what changed."). The dialog closes by itself once a list read since it opened is empty.
- While conflicts stand, Publish and Sync open the dialog instead of trying again, and the panel says so with a **Choose which to keep** button. The engine only resolves conflicts with the upstream, so a conflict from "Bring in changes" keeps the plain next step ("Open it on GitHub, or ask whoever manages the site.", after "Publish your edits first" when there's local work), and that action stays disabled while `gitStateSignature` says nothing has changed (no fetch, commit, edit or branch switch since), because trying again would only stop the same way.
- **The palette's Publish and Sync** go through the same guards as the buttons (`publishBlocker`, `syncBlocker`): busy, not a repository, not on a branch, nothing to publish, no message, held back. When one applies, a toast says why. LeftSidebar keys `ChangesPanel` by project, so a draft message or notice never follows you to another project.
- **Publish checks fields first.** Before publishing, `entriesNeedingAttention` (`lib/git/publish-check.ts`) runs the form's validator over the changed entries (the open one as it is in the editor). If any fail, a confirmation asks "2 fields in “Jordan Ellis” need attention. Publish anyway?" with **Review** (opens the first entry with its messages showing) and **Publish anyway**. It never blocks.
- **Publish includes what it just saved, once.** It saves first, then reads the status again inside the mutation and writes the message from that, so an entry with unsaved edits (not in the status yet) is part of it. With unsaved edits Publish is never "Nothing new to publish". It stays disabled while the field check runs, and ignores presses while a git change is running.
- **Discard changes** on each row confirms "Throw away your changes to “Andrew Dyk”? This can't be undone." (a destructive button) and runs `gitDiscardFile` as a repository change: the open file is saved first (or auto-save would write the old edits back), then reloaded, or closed if it was new. A renamed file has no Discard: it's two paths, and putting one back would leave the other behind.
- **Titles** are shortened to 40 characters with "…" (`shortTitle`, `useEntryLookup().titleFor`) in lists and messages; the pre-filled Publish message uses whole titles (`fullTitleFor`).
- **Pull requests** are offered only when `gitCommitsAheadOfDefault` is above 0 (GitHub refuses an empty one). The suggested title is the latest non-merge commit on the branch (`pullRequestTitle`), else "Changes from {branch}". While a pull request's checks are pending, `usePullRequestsQuery` reads them again every 15 seconds while the window is focused, so the card turns green by itself; it stops when none is pending or the writer signs out.
- **Merge** stays disabled while the branch has changes or commits that aren't on GitHub ("Your latest changes aren't on GitHub yet. Publish first.").
- **`GitMainView`** draws the diff or History over the editor, which stays mounted underneath (see "Keep stateful panels mounted" in the architecture guide). Escape, the close button and opening a file return to the editor. History hides the frontmatter panel while it's open, for the width, and shows it again after if it was showing.
- **`CommitGraph`** lays rows out with `layoutGraph()` (`lib/git/graph-layout.ts`, pure and tested) and draws all lanes as one SVG behind the rows, so lines run unbroken between rows. Lane colours are the `--git-lane-0…7` tokens, used through full class names (`stroke-git-lane-3`) so Tailwind finds them.
- The palette's Publish and Sync are DOM events (`git-publish`, `git-sync`) that `ChangesPanel` handles with the same handlers as its buttons, because they need the panel's message and sign-in state.

The words are deliberately plain: Publish, Sync, Open pull request, Merge, "not on GitHub yet". Git terms appear only in History.

## Signing in

`lib/git/sign-in.ts` drives GitHub's device flow through the store, so the sheet can open from the panel, Preferences and Open from GitHub alike: it asks Rust for a code, shows it, and waits while Rust polls GitHub. Each start or cancel bumps an attempt counter, so a wait that's been cancelled can't touch the sheet when it finally returns. Closing the sheet calls `githubCancelSignIn`, which stops the poll on the Rust side and keeps any stored sign-in.

## Open from GitHub

`OpenFromGitHubDialog` lists the signed-in writer's repositories (search, or paste a GitHub link; SSH links become HTTPS so the sign-in is used), clones into `~/Sites` (created if it's missing) or a folder the writer picks, can't be closed while downloading (`cloneInProgress`, so the result is never lost), shows progress from the `git-clone-progress` event, and, before opening the result with `projectStore.setProject`, prepares it if it's an Astro site ("Preparing your site…": `devServerPrepare` installs dependencies and runs `astro sync`), so its forms have their schemas at once. **Skip** stops a preparation that hangs (`devServerStop`) and opens the site anyway, saying some fields may be missing until Preview runs. Long folder paths are cut in the middle (`shortenMiddle`) with the full path in the tooltip. `useSitePreparation` (Layout) does the same once per launch for any opened Astro site with collections but no `.astro/collections` schemas (`lib/dev-server/prepare.ts`), deciding only once the collections are listed; its toast has a **Stop** action. Neither `npm ci` nor `astro sync` changes a tracked file (`.astro/` and `node_modules/` are ignored, and `npm ci` never rewrites the lockfile).

## Styleguide

`src/styleguide/GitSection.tsx` has the History view, diffs, the Changes tab in its main states, the sign-in sheet, the Open pull request dialog, Open from GitHub and the Resolve dialog (`bun run app styleguide git-history git-diff git-changes git-changes-more git-sign-in git-open-pull-request git-open-from-github git-resolve git-resolve-again git-changes-conflicts`).
