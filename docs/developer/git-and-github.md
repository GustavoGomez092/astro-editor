# Git and GitHub

The Rust engine behind the Git panel: status and diffs, sync and publish, branches, the commit graph, GitHub sign-in, pull requests and cloning. Everything is behind the **Show Git and preview tools** preference in the UI; the commands themselves are always registered.

## Modules

- `src-tauri/src/git/`: git through libgit2 (`git2`, vendored), so it works on a Mac without the Xcode command-line tools.
  - `mod.rs`: the IPC types, `open` (finds the repository containing the project, so a project in a subfolder of a repo works), and shared helpers.
  - `status.rs`: branch, upstream, ahead/behind, default branch and changed files.
  - `diff.rs`: one file's diff, either the working tree against `HEAD` or a commit against its first parent (a root commit against the empty tree).
  - `remote.rs`: fetch and push, and the credentials callback.
  - `sync.rs`: sync, publish, "bring in changes from the default branch", the commit author, and counting commits behind and ahead of the default branch.
  - `conflicts.rs`: the files that conflict with the upstream, and resolving them by keeping one whole-file version of each.
  - `discard.rs`: throwing away one file's local changes.
  - `branches.rs`: the branch list and safe checkout.
  - `log.rs`: the commit graph and commit details.
  - `clone.rs`: cloning into a new folder, with progress.
- `src-tauri/src/github/`: the GitHub REST API.
  - `http.rs`: the client. Base URLs are injectable for tests, and errors become plain sentences.
  - `auth.rs`: the device flow, the token store and the cached profile.
  - `repos.rs`: which repository `origin` is, and the user's repositories for cloning.
  - `astro_check.rs`: which of those repositories look like Astro sites (GraphQL, see below).
  - `pulls.rs`: list, open and merge pull requests.
- `src-tauri/src/commands/git.rs` and `github.rs`: thin Tauri commands. libgit2 calls are blocking, including the network ones, so every git command runs on `tokio::task::spawn_blocking`, inside `git::with_repo`, which holds a per-repository lock for the whole command. A timed sync and a Publish on the same repository therefore never interleave.
- **Quitting waits for git.** `quit_app`, the quit timeout and `RunEvent::Exit` call `git::hold_all_repo_locks`, which waits for every repository's lock and keeps it, so no command is killed part-way through a write and none starts after. Every call shares one 30-second deadline, set by the first, so the second (`RunEvent::Exit`) adds no wait of its own: after the deadline it only tries each lock once. A process killed mid-write leaves `.git/index.lock`, and git refuses to touch the repository until it's removed. As a backstop, the first time a repository is opened in a session `with_repo` removes an `index.lock` older than 10 minutes once it holds the lock (so no command of ours is using it), and logs it. The threshold is long because a `git commit` waiting on its editor holds the lock while the editor is open; a lock that old at first open is almost certainly a leftover, and an app that can never publish again is worse.

Paths in `ChangedFile` and the `path` argument of the diff commands are relative to the repository root, with forward slashes.

## Safety rules

The anti-goal is losing a writer's edits, so these hold everywhere:

- **No operation discards uncommitted changes.** There's no hard reset anywhere in the engine, and only two forced checkouts, both limited to literal paths (`disable_pathspec_match`, so a `*` in a name matches only itself):
  - **Discard** (`discard.rs`) forces back the one file the writer asked to throw away, after the UI has confirmed it, and only after checking the path stays inside the repository.
  - **Putting files back** (`git::undo_checkout`): when a merge, fast-forward or resolve has checked out its result but then can't move the branch, it forces back the paths that differ between the two trees, and nothing else. It runs only when the branch still points where it did (`move_branch_or_undo` re-reads it); if something outside the app moved it, the files are left as they are and the message says to run Sync again, because forcing the old versions back would look like edits undoing the new commit. Those paths had no local edits a moment earlier: a safe checkout just wrote them, and Sync's and resolving's pre-checks refused any path with a local change.
- **Checkouts and fast-forwards use libgit2's safe checkout, with `overwrite_ignored(false)`** (`git::checkout_safely`). Safe mode alone happily replaces an ignored file, such as a local `.env`, when the target tracks a file at that path. libgit2 checks every file before it writes any, so a refusal leaves the working tree as it was; the conflicting paths come from the checkout notify callback and are named in the message.
- **Fast-forwards are checked before they're tried.** Sync refuses (`blockedByLocalChanges`) when an incoming change touches a file that's changed locally, even if git could carry the edit across.
- **Merges happen in memory first** (`merge_commits`). If the result has conflicts, nothing has been written, so "abort and restore" is simply not continuing. Only a clean result is committed and checked out. Diverged branches are merged only when the working tree is clean.
- **Branches move only from where they were.** Fast-forwards and merges update the branch with `reference_matching` against the commit they started from, so a commit made meanwhile is never dropped (the per-repository lock makes this rare; this makes it impossible).
- **Resolving conflicts keeps whole files.** `gitConflicts` lists the files an in-memory merge of `HEAD` and its upstream (as last fetched) can't combine, with both versions (text only; a binary file has `binary: true` and no text; a side that deleted the file has `null`). `gitResolveConflicts` repeats that merge, takes the chosen side's index entry for each conflicted path (or removes the path, if that side deleted it), commits it with both parents ("Combine changes from GitHub") and checks it out safely. It refuses, changing nothing, if any conflicted path has no choice, and comes back `blockedByLocalChanges`, naming the files, if any path the merge changes has an uncommitted edit or an untracked file, checked before anything is written (a safe checkout alone lets a file through when its working copy already equals the result). It doesn't fetch or push: the writer chose between the versions they were shown, and the next Publish sends the merge (if the upstream moved meanwhile, that Publish combines again as usual). It only covers the upstream, not a conflict from "Bring in changes from main".
- **Discarding touches one path.** `gitDiscardFile` restores a file in `HEAD` with a forced checkout limited to that literal path (`disable_pathspec_match`, so a `*` in a name matches only itself) and re-stages it, or deletes a file that isn't in `HEAD`. A rename is undone on both sides. Paths are refused if they're absolute, contain `..`, point into `.git` or lead out through a symlinked folder. A file without changes, or an ignored one, is left alone. The UI asks first; this is the one deliberate exception to "never discards", and it only ever does it for the path it's given.
- **Publish commits before it touches the network.** Once the commit exists, every later failure (offline, conflict, rejected push) comes back as `pushed: false` with a message, not as an error, so the UI can say the work is saved on this computer.

Merges are always merge commits (sync, publish, bring in changes, pull requests), so a long-lived branch like `staging` never drifts from the default branch. Their messages are for writers: "Combine changes from GitHub" (or from the remote's name, `origin`, elsewhere) for sync, publish and resolving, and "Bring in changes from main" for the default branch.

## Authentication

- **Sign-in is the OAuth device flow** for an OAuth App, which needs no client secret. The client ID is compiled in from `ASTRO_EDITOR_GITHUB_CLIENT_ID` (`option_env!`, so builds without it still compile) and overridden by `advanced.githubClientId` in `global-settings.json`, which Rust reads directly. The scope is `repo`. Tokens from this app don't expire; a refresh token or expiry in the response is ignored.
- **`githubDevicePoll` polls inside the command** at the interval GitHub gives, adding 5 seconds on `slow_down`, until the code is approved, denied or expired. Signing out, starting again or `githubCancelSignIn` (closing the sign-in sheet) cancels it (a generation counter plus a `Notify` that wakes the sleep). Cancelling keeps a stored token.
- **The token lives in the OS credential store** (`keyring`: Keychain on macOS), service `<app identifier>.github`, account `token`, so dev and release builds keep separate sign-ins. It's never written to preferences or logs. `CachedStore` keeps it in memory after the first read and holds its lock during that read, so two callers racing at startup cause one Keychain read (one prompt on a build the Keychain doesn't trust yet), not two.
- **Keychain access can block,** so it never runs on the async runtime: `Auth` goes through `spawn_blocking`, and the git commands call `auth::token()` inside their blocking work.
- **The profile is cached** after the first `/user` call, in memory and as `{id, login, name}` in `github-profile.json` in the app's data folder (it isn't secret), rewritten on sign-in and each successful `/user`. A 401, signing out, or finding no token deletes it. When GitHub can't be reached, status reports signed in without a profile, so being offline doesn't look like being signed out, and `cached_user()` falls back to the saved profile, so an offline Publish can still sign its commit.
- **Git network operations** send the token as `x-access-token` for github.com over HTTPS only (never `http://`, where it would go out in the clear). The check (`remote::is_github_https`, used for the URL libgit2 hands the credentials callback too) refuses any URL containing `@` or `\`, then parses it with `url::Url` and wants the scheme `https` and the host exactly `github.com`. Parsing alone isn't enough: libgit2 takes the host after the last `@` and percent-decodes the user part, while URL parsers treat `\` as `/`, so `https://github.com\@evil.example/…` and `https://github.com%2F@evil.example/…` read as github.com to the parser but connect to evil.example. GitHub owner and repository names can't contain either character, so nothing real is refused, except a github.com URL with a user name in it (`https://user@github.com/…`), which goes to git's credential helper instead. Other hosts use git's credential helper. Each credential is offered once, because libgit2 asks again after a rejection and would otherwise loop.
- **The commit author** is git config's `user.name` and `user.email` when both are set, else the GitHub profile with its no-reply address (`<id>+<login>@users.noreply.github.com`). The profile is fetched only when the config has no identity. When git config is missing `user.name` or `user.email`, the app writes the profile's (only the missing ones) into the repository's own config after sign-in (for each repository opened so far that no command is using; a busy one is skipped, not waited for), after a clone, and on Publish, Sync, Bring in changes and resolving conflicts, so commits made later in a git tool carry the same name. It's best effort; commits fall back to the profile without it.

`github::auth::token()` is the token for any module that needs it. Logic functions take the token as an argument, so tests never touch the Keychain.

## Gotchas

- **No SSH.** git2 is built without its `ssh` feature, which would link OpenSSL dynamically on macOS and break the app on Macs without Homebrew's OpenSSL. A github.com SSH origin (`git@github.com:owner/repo.git`) is fetched and pushed over `https://github.com/owner/repo.git` with the token, through an anonymous remote with explicit refspecs, so `origin/*` still updates and the configured URL is never changed. Any other SSH host gets a plain message saying only HTTPS remotes (and GitHub SSH remotes) are supported.
- **Network timeouts** are set once at startup (`git::init_network_timeouts`: 15 s to connect, 60 s per read), so a stalled connection can't hang Publish.
- **One idea of "upstream".** `status::upstream_of` is the configured upstream, else `origin/<branch>` when it exists. Status, the branch list, Sync and Publish all use it, so the panel's ahead/behind matches what Sync and Publish will do. Publish still writes the upstream to the config on first push.
- **Push rejections:** a remote's refusal comes through `push_update_reference`. Only a non-fast-forward ("non-fast-forward", "fetch first", or libgit2's `NotFastForward` from a local remote) says GitHub has changes to sync first; anything else (protected branches, hooks) is shown as "GitHub refused the update: <reason>".
- **"Bring in changes from main" is offered from `gitCommitsBehindDefault`**: the default branch's commits (as last fetched, else the local branch) that the current branch doesn't have, counted with `graph_ahead_behind`, so it doesn't depend on how much history the UI has loaded. `gitCommitsAheadOfDefault` is the other direction, whether there's anything for a pull request. Both are 0 on the default branch itself.
- **Messages name the next step only when it helps**: a blocked sync suggests publishing first, but not when the file in the way is ignored (publishing can't help; the message says a file that isn't part of the site would be overwritten), not when the checkout failed for another reason (it says what went wrong), and a conflict with the default branch doesn't point at Publish. A file's path is never followed by a full stop, because the frontend shows a quoted entry title in its place, and the closing quote brings its own.
- **Repository info is worked out locally** from `origin`'s URL and the default branch (`origin/HEAD`, else `main`, else `master`), so it works offline and before sign-in. Fetch records `origin/HEAD` when a repository doesn't have it.
- **A 404 or 403 from GitHub means "no access"**: GitHub answers 404 for private repositories the token can't see. Both become "Your GitHub account doesn't have access to this repository".
- **Pull request checks are best effort.** The list combines the head commit's combined status and its check runs; if either request fails, that part counts as no checks rather than failing the list. The list endpoint leaves out `mergeable`, so each open pull request is fetched once more.
- **Pagination only follows `Link` URLs on the API's own origin,** because the token goes with the request.
- **Clone creates the parent folder if it's missing** (the default, `~/Sites`, doesn't exist on a fresh Mac), **refuses a folder that already has files** and removes what it created if it fails. Progress arrives as `git-clone-progress` events (`CloneProgress { received, total }`, at most about 100 per clone).

## Astro-only repository list

Open from GitHub lists only Astro sites by default (a switch, "Show all repositories", turns the filter off; the choice is kept in `localStorage`).

- **Detection** (`github::astro_check`, command `githubCheckAstroRepos`): GraphQL (`POST https://api.github.com/graphql`, the same client and token handling as the REST calls), 50 repositories per query (25 when there are more than 300), at most three queries in flight, using aliases (`r0…`) and variables for owner and name. A repository is Astro when its default branch's root (`HEAD:`) has `astro.config.{mjs,ts,js,cjs,mts,cts}` (matched as `... on Blob`, so a folder of that name doesn't count), or its root `package.json` lists `astro` in `dependencies` or `devDependencies`. Only `package.json` is fetched as text (a leading byte order mark is ignored).
- **Answers** are `astro`, `notAstro` or `unknown`. An empty repository (no default branch) is `notAstro`. `unknown` is a repository the token can't read, a GraphQL error for it, or a `package.json` that is over 200 KB, cut short or not JSON. A query that fails as a whole makes only its repositories `unknown`, so answers from the other queries are kept; a `Retry-After` (up to 60 s) is waited out once. The whole call stops waiting after 90 seconds (what's unanswered is `unknown`), and a 200 whose `data` is null or missing counts as a failed query (its `errors` message is logged). Only when every query failed does the command return an error.
- **Cache** (`lib/git/astro-sites.ts`): definite answers are saved in `localStorage` by `owner/name` with the repository's `pushedAt` (else `updatedAt`), so reopening the dialog is instant and a repository is looked at again only after a push. The saved text is parsed once per change. `unknown` is never saved, so it's retried; entries for repositories no longer in a fully loaded list (under 1,000) are dropped when answers are saved.
- **UI** (`useAstroSiteStatus`): one TanStack query asks for the repositories without a saved answer. Rows without an answer are "Checking…" (muted, still listed); a failed request (logged, shown as `unknown`) and a result with `unknown` in it are asked again soon (the next time the dialog opens). With the filter on, `notAstro` rows drop out, `unknown` rows stay as "Couldn't check", and the repository picked for download always stays. A polite live region says "Showing 3 Astro sites" (plus "(1 couldn't be checked)" when some are unknown) when the check finishes or the switch changes, not as you type in the search box. The styleguide's Open from GitHub section seeds these states with `?astro=checking` and `?astro=none`.

## Testing

Tests sit beside the code. Git tests build temp repositories and bare "remotes" with git2 and `tempfile` (`git/test_support.rs`), with a fixed identity in each repo's own config, so they don't need a `git` binary or the developer's config. GitHub tests (including the GraphQL ones) use `mockito` through the injectable base URLs and an in-memory token store; nothing talks to the real network or Keychain. An unreachable remote is `http://127.0.0.1:9`.
